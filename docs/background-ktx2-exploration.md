# KTX2 background animation: deferred exploration

Recorded 30 October 2026. **Status: exploration only; implementation is deferred.**

Consider an optional KTX2 array output for the same phase images currently
generated by the [sampled background video workflow](background-loop-prototype.md).
Each phase would become a texture layer instead of an encoded video frame. The
artist would retain independent control over resolution, phase count, loop
duration, sampling side and interpolation. Ribbon and background settings do not
need to match.

## Potential benefit

After loading, a fully resident texture array can select phases directly in the
shader. This could remove ongoing video decoding and changing-frame uploads,
improve seeking/reverse playback, and simplify scene-clock synchronization and
deterministic exports. Neighboring phases can be crossfaded in the shader.

The current [video background adapter](../apps/rivvon/src/services/backgroundClip.js)
draws changed video frames into a canvas and updates a canvas texture. A future
comparison should include optimized direct video-texture playback as well as
this existing path. Hardware video decoding is efficient; better playback or
power consumption from KTX2 must be measured rather than assumed.

## Limits: container, GPU capabilities and memory

KTX2 supports array textures and standard `KTXanimData` animation metadata. Its
header uses a 32-bit layer count; there is no container-level 256-layer ceiling.
GPU limits and practical allocations are more restrictive.

An isolated headless Chrome 156 probe on the development machine reported:

| Configuration | Maximum texture side | Maximum array layers |
| --- | ---: | ---: |
| WebGL2 (Intel graphics through ANGLE/D3D11) | 16,384 | 2,048 |
| WebGPU adapter capability | 16,384 | 2,048 |
| WebGPU device created with default limits | 8,192 | 256 |

These are observations from that probe, not portable guarantees or proof that a
large allocation will succeed. Rivvon's [WebGPU setup](../apps/rivvon/src/modules/viewer/threeSetup-webgpu.js)
requests supported compression features but does not currently request higher
array-layer limits. Its default 240-phase loop fits the default 256-layer limit;
longer sequences such as 1080 phases would need higher negotiated limits or
multiple arrays.

The [current encoder](../apps/rivvon/src/workers/ktx2EncoderWorker.js) uses UASTC
4x4, generates mipmaps, and disables additional UASTC supercompression. Common
transcode targets BC7 and ASTC 4x4 use 8 bits per pixel (one byte per texel).
Approximate payload sizes at that rate are:

| Square size | Layers | Base level only | With full mip chain |
| --- | ---: | ---: | ---: |
| 512 | 240 | 60 MiB | 80 MiB |
| 1024 | 240 | 240 MiB | 320 MiB |
| 1920 | 60 | 211 MiB | 281 MiB |
| 1920 | 240 | 844 MiB | 1125 MiB (1.10 GiB) |
| 3840 | 240 | 3375 MiB (3.30 GiB) | 4500 MiB (4.39 GiB) |

Calculation: `width * height * layers * bytesPerTexel`, with approximately 4/3
of the base-level size for a full mip chain. Small block-padding differences are
omitted. These figures exclude source files, transcoding workspace, CPU copies,
encoder heaps, and other scene textures/render targets.

The generation pipeline's 256 MiB phase-surface budget bounds temporary sampling
surfaces; it does not bound the final animation's playback footprint. An RGBA8
fallback would use four bytes per texel: 1920 square with 240 base-level layers
alone would occupy about 3.30 GiB. Check the actual GPU transcode format before
loading large assets; a silent uncompressed fallback would be costly.

## Mipmaps are an open choice for backgrounds

**Do not assume that a background needs the ribbon texture's mipmap policy.**
The background generally has a fixed placement within the scene, so a
base-level-only representation is a reasonable first configuration to evaluate.

Mipmaps address spatial minification, not whether an object moves. They can
still help when a high-resolution background is displayed at a smaller render
resolution, in a preview, at a different device-pixel ratio/render scale, or in
a smaller export. Fine stripes or high-frequency details can alias even when
the background's placement is stationary. Temporal phase interpolation is a
separate issue; spatial mipmaps do not blend animation phases or reduce the
number of layers.

At approximately native pixel size or under magnification, a full mip chain may
offer little benefit. Omitting it saves roughly one quarter of the full-chain
payload: the 1920-square/240-layer example falls from about 1.10 GiB to 844 MiB.
That is useful, but does not remove the overall memory concern.

If this is revisited, compare base-level-only linear filtering with mipmapped
sampling at native size, substantial downscaling, rectangular cover fitting,
and representative preview/export sizes. Consider selecting a lower-resolution
asset variant at load time for smaller displays. Keep this policy specific to
background assets; textures also used on ribbons may have different scaling and
perspective requirements. The existing encoder's mipmap setting remains as-is.

## Drawbacks and integration work to investigate

- **Download/storage size:** with the current unsupercompressed UASTC encoder,
  file payload would be of similar magnitude to the compressed texture figures
  above. The earlier synthetic 1920-square/240-frame MP4 was only 8.78 MiB.
  Compression ratios will vary with content and encoding settings.
- **Transport compression versus residency:** Zstd or another texture encoding
  may reduce download size without reducing the final GPU block allocation.
  Basis Universal also has texture-video compression techniques, which are a
  separate investigation from our independent-layer UASTC encoder.
- **Loading peaks:** the current assembler collects encoded layers and creates
  combined buffers; the loader transcodes complete arrays and mip levels.
  IndexedDB batching during generation does not eliminate those allocations.
  Multi-gigabyte assets can encounter browser/WASM allocation limits.
- **Residency and reliability:** GPU oversubscription can cause paging, stutters,
  context loss or a terminated tab. Browser APIs do not expose a dependable
  portable measure of currently available VRAM.
- **Quality:** block compression can affect gradients and fine bands. Crossfading
  fewer stored phases may introduce ghosting. These remain artistic choices.
- **Existing infrastructure:** the texture upload route buffers a complete tile;
  large background arrays would need a suitable upload/assembly path. Existing
  motion-interpolation/export caches also retain decoded RGBA layers and would
  need explicit bounds before reuse at these sizes.
- **Startup versus steady-state cost:** resident playback moves work to download,
  transcoding and upload. Encoding time, startup time and playback time need
  separate measurements.

## Possible directions, without an implementation commitment

1. Retain MP4 and evaluate KTX2 as an optional representation.
2. Start with modest phase counts (30/60/120) at 1024 and 1920 square, including
   base-level-only assets. A 60-phase sequence can still span eight seconds;
   rendering may crossfade between phases at the scene's frame rate.
3. Compare identical sampling recipes for startup, transfer size, actual GPU
   format, memory estimates, playback frame times, export speed and visual quality.
4. Evaluate chunked arrays only if longer sequences are important. Keeping the
   current and next chunk resident lowers memory, but reintroduces I/O,
   transcoding and upload scheduling. Splitting arrays while keeping every chunk
   loaded only addresses the layer-count limit, not total memory.

The most promising initial combination is high spatial resolution with a modest
phase count and artist-controlled crossfading. Full-resolution, 240-layer
resident arrays remain a demanding option even without mipmaps.
